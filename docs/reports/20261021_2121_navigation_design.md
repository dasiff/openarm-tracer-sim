Written for: David, who decided N1 to N11 and reviews this before any code is written. Design only: no navigation code exists after this report.

Decision since the first draft (David, 2026-10-21): **mirror Nav2** (option C). Our own small module, behind our navigation interface, using Nav2's algorithms and Nav2's parameter names where an equivalent exists (costmap with inscribed and inflation radius, the Smac 2D A* planner, an iterative smoother and then our B-spline fit, Regulated Pure Pursuit, an obstacle layer fed by observations). Nav2 names and defaults in this report are from my memory of the Nav2 documentation (Jazzy): they are marked "verify" and are checked against the installed version's documentation in the first build step; I did not look them up here.

## 1. What is replaced and what stays

The staging source (`src/staging_source.py`) runs ARMS, PEDESTAL, DRIVE, CREEP_IN, NECK, DONE. Only DRIVE is replaced. ARMS and PEDESTAL (configuration changes in open space, design plan §1), CREEP_IN (under the bench, exact geometry as now) and NECK stay. The target resolution stays as it is: the world model gives the stance (`world.stance(target)`), and the approach spot is the stance moved back by `staging_approach_back_m` along the stance heading (`staging_approach_xy(task_cfg)`).

Today's DRIVE is `_pose_controller` (turn in place toward the goal, a straight line with cross-track correction, turn to the goal yaw, settle) with the ground-truth base pose from `obs["base_pose"]`. It does not look at obstacles: the spawn-to-bench line is open floor by construction. The new module is a path planner and follower with the same job: take the base from where it is to the approach spot at the stance heading.

## 3. How the base is driven now, and how the follower will command it

The staging's DRIVE emits `{"mode": "base", "twist": (forward m/s, yaw rate rad/s)}` once per control tick (150 Hz, 5 physics steps at 750 Hz). The control loop writes it into the base's free joint velocity (`apply_base_velocity`, `src/base_control.py`: world x and y velocity from the twist and the heading, yaw rate, no roll or pitch rate; z left to physics), after the loop's own limits and ramps. So the base is a unicycle (no sideways motion) driven by velocity, not by wheel torques; the lean the checks measure comes from the arms and torso reacting to the velocity changes through the physics.

The follower commands exactly the same interface: a forward speed and a yaw rate per tick. Nothing in the control loop changes. The acceleration limits of the follower sit before the command (as `_slew` does now in the staging), so the loop's own limits stay a second safety.

## 4. World model changes (N3)

- `Entry` gets two optional fields: `outline` (an (N, 2) polygon in the world frame, metres) and `height_range` (z_low, z_high in metres above the floor). An entry with both blocks the floor for the planner when its height range overlaps the robot's height band (0, `h_top`) and `blocks_floor` is true (a property, default true when an outline exists).
- A new kind "obstacle" (besides "object" and "fixture") for things that are neither: an unknown obstacle.
- `found` gets the value "sensor" (the others: map, sim_ground_truth, detector, operator, config).
- `WorldModel.obstacles()` -> the entries that block the floor; `WorldModel.version` (a counter that increases only when an obstacle entry's outline or height range actually changes, so a source that rewrites the same values every tick does not trigger a replan); `WorldModel.observe_obstacle(outline, height_range, t)` -> adds or updates an entry "unknown_<n>", kind "obstacle", found "sensor" (the interface for N10; fed by the depth task, V1 and V2: anything solid, on the floor and on work surfaces, seen in the eagle camera's depth image becomes an unknown object with an outline and a height range; until that task exists only the tests call it); `WorldModel.observe_free(region, t)` -> removes the sensor entries inside a region the camera currently sees empty (N-Q7, M058: an unknown obstacle is removed when the camera sees that space empty and kept while out of view, no timer; the visible region is the camera's view of the floor and surfaces within its depth range). They stay "unknown obstacle"; naming is LATER (the detector of V3 names an entry when it detects an object on its spot). Unknown objects count for navigation and for the clearance height of C1.
- A fixture source (found "map") fills the fixtures from the scene's collision geometry: the outline is the projected convex hull of each fixture's geoms (reusing `geom_points_world` of `src/furniture_map.py`), the height range its vertical extent. Today `FurnitureMap` reads the geoms directly for the stance finder; the stance finder stays as it is (offline), and the new fixture source and `FurnitureMap` read the same geoms, so there is one geometry, two consumers. Only fixtures are known in advance.
- The planner never holds a second copy of the truth: its grid is rebuilt from `world.obstacles()` when `world.version` changes.

## 5. Planning

**N1 grid.** 2D, `NAV_CFG["cell"] = 0.05` m, over the room (the grid bounds of `FURNITURE_CFG`, +-6 m: 240 x 240 cells). Everything outside is blocked.

**N2 one layer.** Each blocking entry's outline is rasterized into one layer if its height range overlaps (0, `h_top`), where `h_top` is the top of the robot at the drive pedestal height with the arms at the zombie pose (from `nav_footprint`). The open bench therefore blocks its whole outline: A* never drives under an overhang; only CREEP_IN goes under it. An obstacle lower than `min_block_height` does not block (Nav2's minimum obstacle height; N-Q2, M054): 0.01 m, a placeholder until the hardware team says what height the Tracer can drive over (design plan 11).

**N4 footprint and inflation.** `r_in` and `r_out` from the compiled model at the drive pedestal height. A cell is blocked if its centre is closer than `r_in` to an obstacle (a distance transform of the layer), free if farther than `r_out`; in between it is allowed only if the real footprint, rotated to the direction of travel, clears (the per-heading blocked masks of `FurnitureMap.blocked(heading, footprint)`, the obstacle layer dilated by the reflected footprint; computed for the 8 move headings, so the A* edge test is one lookup). The soft cost is Nav2's inflation layer: `cost = 252 * exp(-cost_scaling_factor * (d - r_in))` for `r_in < d <= inflation_radius` (d the distance from the obstacle's surface to the cell centre in metres), lethal (254) inside the obstacle, inscribed (253) when the centre is within `r_in`; start `inflation_radius = r_in + 0.30` and `cost_scaling_factor = 3.0` (Nav2's default for the factor is 10.0, which is made for a small round robot; verify). The planner's step cost uses it through `cost_travel_multiplier`, as Smac 2D does.
Known size of the problem: the footprint corner is 0.46 m from the base origin (`task_config.py`, the stance notes); the chassis and battery top out at 0.41 m with the base resting at 0.153 m; `r_in`, `r_out` and `h_top` are "to be measured" from the model in the first build step (they depend on the arms at the zombie pose, which stick out of the chassis).

**N5 A*.** 8-connected, octile heuristic, step cost = octile distance + the soft cost, from the start cell to the approach spot's cell. No path: a reported failure with the reason, and the module's status is "failed" (no silent fallback to the straight line).

**N6 smoothing, over the whole trip.** Resample the A* path to uniform points (5 cm), then iterate with the update rule of Nav2's `SimpleSmoother` (also the smoother inside Smac 2D), ends fixed: `y_i <- y_i + w_data * (x_i - y_i) + w_smooth * (y_{i-1} + y_{i+1} - 2 y_i)`, with one term added that Nav2 does not have, David's third term of N6, the distance from obstacles: `+ w_obs * repulse(y_i)`, where `repulse` points away from the nearest obstacle with magnitude `max(0, d_soft - d(y_i)) / d_soft` (the clearance field of the grid, bilinear) and `d_soft = inflation_radius - r_in`. Starting values: `w_data 0.2` and `w_smooth 0.3` (Nav2's defaults; verify), `w_obs 0.3`; `max_its 1000`, `tolerance 1e-10` (Nav2's, which would make the 1000 iterations almost always run; we stop when the largest move is below 1 mm), `do_refinement true`, `refinement_num 2`. Then a cubic B-spline through the points (`splprep`, k = 3, parametrized by chord length, smoothing `s = N * (0.01 m)^2`, so the fit is within about 1 cm of the smoothed points): C2, so the curvature is continuous. Nav2 has no spline fit; ours is added for the curvature continuity, the pre-flight verification and the local repair (N7). The corridor, maze and gap tests (section 8) tune the weights; they stay settings.

**N7 verification before the robot moves.** Sample the spline densely: every 2.5 cm of arc length and at every 2 degrees of heading change, whichever is finer. At each sample, take the real footprint at the tangent heading, grow it by the tracking tolerance (`NAV_CFG["track_tol"] = 0.05` m) and test it against the obstacles (the exact outlines from the world model, rasterized at 1 cm for this test only, not the 5 cm planning grid). A failing stretch: restore the A* points around it and refit locally (B-spline local support: only the knots near the stretch change); verify again. If it still fails, that stretch is left unsmoothed (the A* polyline) with stop-and-turn-in-place corners, and the module logs it. The path ends with a straight lead-in aligned with the stance heading (N-Q3, M055): the last `lead_in_m` of the path before the approach spot is a straight segment along the stance heading (start 0.8 m, the maximum lookahead distance, so the follower is lined up before the spot; the points of the segment are fixed in the smoother and the verification covers them). The path also starts tangent to the robot's current heading (the first `lead_out_m`, start 0.3 m, is straight along it), so a robot that must go back the way it faces drives a turning arc, not a spin. An in-place turn is only a fallback, at the end (no room for the lead-in) or at the start (no room for the arc), and only if the full swept circle is checked clear first: the disc of radius `r_out` grown by the tolerance must be free; otherwise the candidate fails ("can't line up", S-new). The verification also checks the curvature: the spline's curvature must not exceed what the regulated speed allows (`kappa_max = omega_max / v_min_regulated`, from N9's measured limits and RPP's regulated minimum speed). If the turn at the start is blocked the plan fails with the reason (the robot is not moved to an unknown place).

## 6. Following (N8) and limits (N9)

**Follower.** Regulated Pure Pursuit with Nav2's parameters (section 11): the lookahead distance is velocity-scaled (`use_velocity_scaled_lookahead_dist`, `lookahead_time`, clipped to `min_lookahead_dist` and `max_lookahead_dist`); the lookahead point on the spline gives the curvature command `kappa = 2 y_l / L^2` (y_l the lateral offset of the lookahead point in the robot frame, L the lookahead distance) and the yaw rate is `v * kappa`; the speed is regulated down for curvature (`use_regulated_linear_velocity_scaling`, `regulated_linear_scaling_min_radius`, `regulated_linear_scaling_min_speed`), near the path's end (`approach_velocity_scaling_dist`, `min_approach_linear_velocity`) and near obstacles (`use_cost_regulated_linear_velocity_scaling`, `cost_scaling_dist`, `cost_scaling_gain`), with the collision look-ahead (`use_collision_detection`, `max_allowed_time_to_collision_up_to_carrot`), and then limited by acceleration limits before it is sent (in Nav2 the velocity smoother, `max_accel` and `max_decel`; the RPP controller itself limits only the angular acceleration, `max_angular_accel`; verify). Our addition: the spline's curvature at the nearest point is fed forward (`omega = v * (kappa_ff + k_fb * (kappa - kappa_ff))`, start `k_fb = 0.5`), which Nav2's RPP does not do; it is a setting and can be switched off to match Nav2 exactly (`k_fb = 1`). Output: forward speed and yaw rate: the same two numbers Nav2 publishes as `cmd_vel` (linear x, angular z). At the end of the path the follower stops within the arrival tolerance, then turns in place to the stance heading (`use_rotate_to_heading`, `rotate_to_heading_angular_vel`; swept circle checked, N7) if the spline's end tangent is not already that heading; arrival (N-Q4, M056): the follower aims for 1 cm and 0.5 degrees (`xy_goal_tolerance` 0.01, `yaw_goal_tolerance` 0.5 degrees, the base at rest for `drive_settle_s`, Nav2's goal checker with `stateful`); a test passes or fails at 1 cm and 1 degree (the budget the maps were eroded for, design plan 3.1 f); the actual position and heading error of every arrival is reported (a table in the test, a line in the episode log), so the margin is visible and not just pass or fail.
**Failures (N-Q5, M057).** "No path" (A* finds none, or no verified path): no retries; the module fails with the reason and the orchestrator asks the operator (or stops, unattended). Drift or a newly seen obstacle (a cross-track error above 5 cm, or a world-model change that touches the unfinished path): stop, replan from the current pose, verify, go (N8), up to `max_replans` times per approach (setting, 3), then the operator. Blocked mid-drive with no way through: first ask stance selection for another stance reachable from here (`can_reach` from the current pose as its first check), then, if there is none, the operator. A replan from a pose where the robot cannot turn and cannot drive a clear arc is also "no way through".

**Limits (N9): measured, not invented.** Today's staging values (0.3 m/s, 0.1 m/s^2 up, 0.15 m/s^2 down, 0.4 rad/s, 0.2 rad/s^2) were chosen gentle ("the base's yaw drifts when it starts to move") and stay within the 1 degree lean bound of `drive_max_lean_deg`. The measurement (`experiments/nav_lean_sweep.py`, first build step, one sim at a time): with the arms at the zombie pose at the drive pedestal height, accelerate, cruise and brake in a straight line, and drive arcs, over a grid of (cruise speed, linear acceleration, yaw rate, angular acceleration), recording the peak tilt of `base_link`; then the same with a beaker held in the hand at the zombie pose (the pose the pick should end in: the zombie pose, design plan §5 and the plan structure B3 of §8; the scripted pick ends at the carry height today, see the 2026-10-21 report; welded to the hand for the sweep, as the test hooks already do), and, because the scripted pick ends at the carry pose until it is changed, also at that pose, and reports both. The largest values whose peak lean stays under 1 degree with a margin (start: 0.8 degrees) are the proposed limits, one set for driving empty and a gentler set for carrying (design plan §13). The table of lean against each limit comes back to you; you approve the values before they become settings.

## 7. Replanning and observations (N10) and the monitors (N11)

- The module compares `world.version` with the version its plan was made on every tick (an integer compare). A change that touches the current path (the new obstacle outline, grown by the footprint and the tolerance, hits the not yet driven part of the spline): stop, replan from the current pose, verify, go. A change that does not touch the path changes nothing.
- The observation interface is `world.observe_obstacle(outline, height_range, t)` and `world.observe_free(region, t)` (section 4). The robot has only three cameras, so the "simulated range sensor" task is replaced (V1, M064): the next task is obstacles and unknown objects from the eagle camera's depth image while driving, if the real camera gives depth (asked, design plan 11); if it is colour only, that task moves to LATER. It marks anything solid, on the floor and on work surfaces, as an unknown object with an outline and a height range (found = sensor, V2, M065). For the tests an injected fake observation calls the interface mid-drive. Depth from a camera that looks ahead and down at the drive pose sees the floor in front of the robot only: what is behind or beside it stays as last seen.
- The staging's clearance monitor (the base and the arms to every obstacle, every few ticks) and the lean check (every tick) stay active in DRIVE exactly as now (N11); they read the simulator's geometry, not the world model, so they stay an independent check of the planner: a planner that believed a wrong map would still be stopped by them.

## 8. Test plan

Fast tests (plain Python, no simulator; made-up maps as grids of world-model entries):
1. Corridor: a straight and an L-shaped corridor a little wider than the robot: the path stays in the middle, the verified spline fits, the follower (a kinematic stand-in for the base) arrives within the tolerance.
2. Maze: A* finds the path; the smoothed spline is verified; a maze with no exit reports "no path".
3. A gap that fits only at one heading (a door narrower than `2 * r_out`, wider than the footprint's narrow side): the path crosses it at the heading that fits; the same gap with the footprint turned is rejected; the A* mask test and the exact verification agree within the cell size (this is where the 5 cm cell shows its quantization, question Q1).
4. The bench approach: the real stance and approach spot, the real bench outline, spawn to approach spot: a path that ends at the stance heading; the end turn (if any) passes the swept-circle check.
5. Replan: an injected observation across the path mid-drive (the kinematic stand-in) forces a stop, a replan, a verified new path, arrival.
6. Smoother terms: each term's effect (a path forced near an obstacle moves away; weights at zero reproduce the A* path), verification fallback (a stretch that cannot be fixed stays unsmoothed with corners).

Added by the answers of 2026-10-21: (a) a gap test at 5 cm and at 2.5 cm: the 2.5 cm grid only if the 5 cm one rejects a gap the exact check accepts (N-Q1); (b) the lead-in: the path ends along the stance heading, and a map with no room for the lead-in falls back to the in-place turn with its swept circle checked, and fails ("can't line up") when that is blocked too (N-Q3, S-new); (c) `can_reach` on the made-up maps and on the bench approach (reach, line up, can't reach, can't line up); (d) removal of an observed obstacle when the camera sees that space empty, and keeping it while out of view (N-Q7, with a fake view region); (e) the pedestal change between stations: back out along the reversed creep-in path, change the pedestal at the nearest clear spot, drive, creep in; no clear spot gives the operator (N-Q8); (f) the failure rules of N-Q5: no path goes to the operator with no retry, three replans then the operator, blocked mid-drive asks for another stance first; (g) the arrival table: the actual error of every arrival against 1 cm and 1 degree (N-Q4).

Simulator tests (one at a time, in tmux, logged, recorded and replayed):
7. A test scene variant with a fixture obstacle (a box) between the spawn and the bench, off by default (a `TASK_CFG` entry; the default scene and every existing baseline stay untouched). The robot drives around it and arrives.
8. An injected fake observation mid-drive in the sim (a sensor obstacle appears on the path): the robot stops, replans, goes, arrives; the clearance monitor and the lean check stay green.
9. The lean measurement of N9 (section 6), the table for your approval.
10. Arrival accuracy at the approach spot against the stopping-error stand-in: the position and yaw error at arrival of the new module against the scripted DRIVE's, over repeated runs from the spawn (and from two other start poses); the follower aims for 1 cm and 0.5 degrees, the test passes or fails at 1 cm and 1 degree, and every arrival's error is reported (N-Q4). The simulator gives the base pose exactly (ground truth), so this measures the follower and the planner, not the localization: how the real robot localizes with cameras only is open (V4, section 10).
11. A full pipeline run to success with the new module (the real plan: navigation, pick, navigation, place), recorded and replayed bit-identically; and the existing suite unchanged with the default (no provider) staging.

Build order (each step committed, tested, one decision-log row each): footprint and radii; world model fields and the fixture source; grid and A*; smoothing, spline and verification; follower; module and the staging seam; test scene; lean sweep (you approve the limits); the simulator tests; the full run.

## 9. Pedestal changes between stations (N-Q8, M059)

The arms and the pedestal change only in open space (design plan 1). When a step needs another pedestal height than the current one, the navigation module does: back out along the reverse of the path the creep-in took (already checked with the exact geometry) to the nearest clear spot (a spot where the configuration change's whole path, arms and pedestal, is clearance-checked clear on a scratch copy, as the staging's ARMS and PEDESTAL phases do now); change the pedestal there; drive to the approach spot; creep in. Only if no clear spot exists does the step go to the operator. The staging's phase order stays (ARMS, PEDESTAL in open space; DRIVE; CREEP_IN; NECK); what is new is that the PEDESTAL phase can run in the middle of a trip, after a back-out.

## 9a. Risks I see

- A 5 cm cell is coarse next to a 0.46 m footprint corner: A* may reject a marginal gap (false reject) that the exact check would accept; the verification catches false accepts only. Option: a 2.5 cm cell (four times the cells, still fast on a 240 x 240 room).
- The footprint depends on the arms: the zombie pose keeps the forearms close, but the footprint must be recomputed if the home pose changes (the code derives it from the compiled model and the config, so it follows).
- The base is velocity-driven in the sim: collisions with a mis-modelled obstacle push through the velocity command (the sim's contacts and the contact monitor log them); the real base will behave differently at a contact. The clearance monitor stops the stage first.
- Replanning from a pose where the robot cannot turn in place (the swept circle blocked) has no good answer: the plan fails with the reason (question Q5).

## 12. Stance selection: its own module (S1 to S6)

**S1. A separate swappable module** (design plan 8 D4 item 5 gets one more: planner, stance selection, navigation, manipulation, checker, world model). It runs before navigation and hands navigation a stance; navigation never sees the objects. This extends the stance deviation already on record: the paper navigates to the target phrase, our arm-only VLA needs a stance that reaches everything the next manipulation group touches.

### 12.2 Where the orchestrator calls it (S2, B1 to B3, S-Q10, S-Q11)

With the plan structure of design plan 8 (B1, M045) every pair of consecutive manipulation steps has a navigation step between them, possibly null. At the start of a navigation step the orchestrator looks ahead: the NEXT manipulation step (and its group, if the plan has one). With B1 the look-ahead for a place step happens after the pick, so the hand contents are already in the world model and nothing special is needed for "the object in the hand" (S-Q10, M062); the grounding of the next step's phrases runs before driving and again at dispatch, as now, in case something moved. It builds the task points (12.1) and first asks the selector whether the CURRENT stance passes every stance check for those points (reach, view, clearance: the layer 3 checks at the current pose, 12.3 b): if it does, the navigation step is NULL (B2, M046): the base does not move, the arm does NOT go to the zombie pose, and the selection is not run; staying put is preferred over a better-ranked stance elsewhere. Otherwise the manipulation step before it ends at the zombie pose (B3, M047: carrying always happens at the zombie pose), the selector runs (12.3) and its stance goes into the navigation step. If no manipulation step follows (the end of the plan), the target phrase is resolved through the world model to a location's stance, as today. If no stance passes, the plan stops with the reason, out of reach or out of view (B6, M050). The eagle camera frames once per step after parking; at a null step it may reframe while the arm pauses, only if the next step's targets need it (B5, M049).

**Longest-run selection (L1, L2; David, 2026-10-21, message 3; M068, M069).** At each non-null navigation step the selector does not pick a stance for the next step alone: it first tries ONE stance for the points of the next k steps together (k = the run cap, `STANCE_CFG["run_cap"]`, default 4), then k-1, down to 1; the first k that passes wins, and the navigation steps between the steps of that run are NULL (the base stays, the arm does not go to the zombie pose, B2). The step order stays the LLM's: nothing is reordered; this gives the fewest moves for a fixed order. The objects of the later steps of the run are grounded early (at the start of the run), and the rule below covers their changes. Two notes on the design: (1) where a run stops is decided (R7, M071 to M073, below); (2) the trials are nested (a stance that passes the points of k steps passes the points of every shorter prefix), so layer 2 need not run k times: the per-step regions of the map query are computed once and intersected one more step at a time (k = 1, 2, 3, 4 for the prefix, tried from the longest), and the layer 3 results of a candidate for the checks that depend on one step only (the clearance and reach of that step) are kept between the trials; what costs again is the view check (neck, occlusion, framing) of a longer run, because more targets must be in the picture, and the IK verification, which covers more points. At the worst, four selections per non-null step add to the run-time budget of R2.

**Where a run stops (R7, David, 2026-10-21; M071 to M073).** (a) A run may continue past an LLM-written navigation step whose target grounds to an object, or to that object's location, that the NEXT manipulation step uses (for example "navigate to the hotplate" before "place the beaker on the hotplate"). That navigation step is then null if the run's stance serves it, the same as an inserted one (B2). The reason: the LLM writes "navigate to X" before each object, as the paper's prompt teaches it, so most of its navigation steps are not a real change of place; and our stances come from the next steps' objects, not from the navigation phrase (S2). Without this, the live plan (navigate to the beaker, pick, navigate to the hotplate, place) would choose the pick's stance for the pick alone and could need an extra move: with it, the run starts at "navigate to the beaker", covers the pick, the navigation step to the hotplate (null), and the place, and one stance is looked for for the points of both steps. (b) A run stops at any other LLM-written navigation step (a target the next manipulation step does not use, or no manipulation after it): that is a real change of location. (c) A run stops at a step whose object is not in the world model yet (no position to plan for; that step needs a search first). A null LLM navigation step still leaves the robot where the target is. In the code of the look-ahead this is a loop over the plan's steps from the current one: add a manipulation step's points, skip a navigation step if its target grounds to an object (or that object's location) used by the next manipulation step, stop at any other navigation step or at an ungrounded object, up to the run cap.

While the robot is on the way or on arrival, at every world-model update of an object the next step needs, layer 2 checks whether the current stance (or the planned one) still reaches that step's task points with margin; if not, the stance is re-selected and the navigation replans from wherever the robot is (S-Q11, M063). Objects are assumed to stay where they were last seen between sightings; tracking moving objects (a Kalman filter) is LATER. A failed selection is a failed navigation step (not retried, then the operator or the stop, design plan 8 D4 item 2) with the selector's reason.

### 12.3 Selection (S4, as replaced by David on 2026-10-21)

a. **Layer 2** (the map query on the reachability maps, design plan 3.4: `find_stances`) runs live and ranks the candidates by the design plan 3.4 ranking rule (both arms reaching every point first, then by the reachable pedestal range (S-Q9, M060), then the distance to the edge of the valid region).
b. **Layer 3** checks the candidates best first and the first that passes wins. The FIRST layer 3 check of a candidate is whether navigation can reach its approach spot and line up (`nav["can_reach"](stance)`, planning only, section 2; S-new, M061): if not, the candidate fails ("can't reach" or "can't line up") and its neighbourhood is skipped. Then, for the candidate: at each pedestal height of its valid range, the cheap checks first (zombie pose clearance, the placed object's clearance), then, where those pass, the neck solves (repeatability), the pixel occlusion renders and the framing slack; the heights that pass form runs, the longest run is the passing range and its middle the chosen height; the passing range must be at least `min_passing_range` (S-Q9, M060: placeholder 4 cm; a candidate with a narrower range fails); then the IK along the whole path (the arm against itself, the hand and fingers against the furniture, the joint margin).
c. **Neighbourhood skipping.** When a candidate fails, every candidate within the skip radius of it is skipped for this pass. The radius is a pair, a distance on the floor and a heading difference (a candidate is within it when both are within), setting, start 10 cm and 10 degrees.
d. **Shrinking passes.** If a pass ends with no stance, halve the radius and pass again over the candidates not yet checked (a candidate is never checked twice). Continue down to the map query's grid spacing (its cell size and its heading step, `STANCE_CFG`), where nothing is skipped: the last pass checks every remaining candidate.
e. **The floor.** Candidates whose layer 2 score is below the floor are never tried. The floor is a setting, default 1 cm on top of the margins already eroded into the maps (design plan 3.1 f). Section 12.5 has the candidates' scores for the current scene so the floor can be set.
f. **Only when the last pass ends with no stance:** stop and report the reason ("no stance reaches all objects of the group", with the failing check of each candidate checked).
g. **Log, per pass:** the radius, the candidates checked, and why each failed (which requirement, with its number).
h. LATER (design plan 10): a skip radius scaled by how badly a candidate failed.

What this needs from the map query. `find_stances` today returns a thinned list (non-maximum suppression, `nms_distance`, at most `max_stances` per heading), which is a ranked short list; the passes of d need every grid candidate above the floor, in rank order, as a lazy iteration (a candidate is a floor cell, a heading, the pedestal range there). The module therefore gets its own query on top of `region_scores` (the per-heading arrays of scores that `find_stances` itself is built from): `candidates(points, floor)` yields (x, y, heading, pedestal range, arm, score) best first, without the thinning. The skipping replaces the thinning: a failed candidate takes its whole neighbourhood with it, instead of the list being thinned before the layer 3 sees it. How many such candidates exist above the floor is in 12.5. Cost note: every pass walks the remaining candidates in rank order; the cheap layer 3 checks reject most quickly (a clearance check is milliseconds), the slow ones (neck solves and renders, the IK) run only for the survivors, so the worst case is bounded by the number of candidates that pass the cheap checks, not by the number of candidates.

### 12.4 How the current stance relates to it

Today's `TASK_CFG` entries (`staging_xy`, `staging_yaw`, `pedestal_q`, `staging_approach_back_m`) are the output of this selection for the current scene, found by `experiments/home_pose_search.py --finder 1` and typed in (design plan 3.4, 2026-10-20). With the module they stop being inputs: `world.stance(target)` for a location with a manipulation group next is replaced by the selector's result. The proposal for the transition: (1) the selector is built and run on the current scene; its output must equal today's stance within the finder tolerance (a test: x, y within 2 cm, heading within 2 degrees, the pedestal command inside today's passing range 0.10 to 0.21); (2) the `TASK_CFG` entries are then kept only as that test's expected value (renamed `expected_staging_*`) and as the stance of a location target with no manipulation (the scripted fallback); (3) the selector's result is cached by a hash of its inputs (the scene's furniture and object poses, the zombie pose, the task points, the map files' build summary) so a repeated episode with the same scene does not pay the selection time again, and the cache entry is logged with its hash. The cache is an optimization, not a source of truth.

**What it means for the module.** The cost is in four places: layer 2 (about 7 s per heading), the neck solves (6.8 s per height), the IK verification (about 130 s) and the occlusion renders (2.5 s per height). The cheap checks are three orders of magnitude cheaper, so the neighbourhood skipping (S4 c, d) pays off most when it skips candidates before the neck solves and the IK; a candidate that fails the cheap checks costs under half a second. A null test of the current stance (B2) is a layer 3 check of that stance and costs the whole 235 s if it passes: R2 in section 10 lists the options (a cache, fewer neck solves for the null test, a heading window, the IK only after the cheap checks pass).
