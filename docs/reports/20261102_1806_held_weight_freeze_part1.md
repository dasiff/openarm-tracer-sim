## Choices I made (please check)
1. Signatures: the new functions take the model and the side, like the rest of the module, and `is_load_changing` also takes the time t (it needs simulation time). The brief said "taking the arm side"; the side is taken.
2. Ramp-out start: a `set_target` to 0 from a held mass sets the flag. This keeps the rule "skills only call set-target". Side effect: if a pick ever started while a mass was still held (not seen in the normal flow), its approach would stay frozen until the gripper opens or the ramp in ends.
3. Reset and running ramp: `is_load_changing` is True during any ramp, so a reset clears the flag but a ramp still running keeps the freeze until it ends. The reset still zeroes the correction at once, so "reset wins" holds for the value. This is the reading that keeps both rules in your brief; say if you want the freeze to end at the reset too.
4. Ramp-in end: once a ramp reaches a nonzero target, the freeze is off, even if the flag was set. This is how "ends automatically" is built.
5. Run start: the existing `clear_held_mass` (src/gravity_ff.py:52-55, called from src/control_loop.py:376) calls `held_mass_ramp.reset`, which clears the freeze too. No change there.
6. The trim update became its own function `_sag_trim_step`, because the guard has to sit in a function with no phase names and `step_inner` has them. Listed in the file table above.
7. Decision rows M224 to M228 were committed in the step 1 commit, before the build, as your order asked. The rule "a row in the same commit" is met in spirit only.
