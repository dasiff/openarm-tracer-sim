# Per-check seed for the stance check (M283), 2026-11-09

Decision (David, 2026-11-09): the stance check stays random. Each computed check takes its own seed from the clock and saves it, so the check can be replayed. Checks no longer share one stream. Decision row: docs/mpvi_decisions.md M283.

## What changed (commits 86c4666, a1226e4)

- src/full_check.py: `check()` takes `seed`. A computed check (not a cache hit) uses `FULLCHECK_CFG["seed_pin"]` if set, else `time.time_ns()`. It builds `self.rng = default_rng(seed)` before its snapshot. The seed is written to checks.jsonl as an `event: check_start` line (record id, seed, stance) before the check runs. `res["seed"]` and the record's `seed` field carry it. Failed checks' group runs (`only=g`) pass the same seed. The fixed seed 11 is gone from the check path (`self.rng = None` in the constructor).
- src/task_config.py: `FULLCHECK_CFG["seed_pin"]`, default None (clock). A number pins every check to it.
- experiments/stance_failure_replay.py: refuses records without a seed; rebuilds the generator from `rec["seed"]` and passes it to the whole check and to each group run.
- experiments/stance_failure_order_test.py (new): runs given rows in one process, each with its saved seed pinned, no logs.
- src/stance_failure_log.py `run_header(None)` says the stream is per check; the six-run script uses it. Other pipeline/mock test headers still print `run_header(11)` (a seed-11 state that no longer governs checks); left unchanged.

## Where the random draws are (check path)

Only two: src/full_check.py `_solve_pose_point` (random starts, `self.rng.uniform`) and `_solve_stance` (random starts). Both now use the per-check generator. No other draw found on the check path (grep of src/ and experiments/; `home_variation_seed` in task_beaker_hotplate.py is a scene-building draw, not on the check path).

## Cache

The cache key does not include the seed (unchanged). A cache hit returns before any seed is taken, so it draws nothing. A cached answer keeps the seed it was computed with (`res["seed"]` is stored in the cache entry), so the record of that computation is the one to replay.

## Findings

1. The order test (fresh process, build_points, pinned seed) gives the same answer as the logged record for rows 17, 18, 21 and 45, in both orders. A check's answer does not depend on the checks run before it in that process.
2. The replay script does not reproduce the record for row 18 (different failing stance and point) or the ik group for rows 37 and 45. It rebuilds the state from the record and does not call build_points, as the order test does. Its cause is not found; a run to separate the two (replay with build_points first, and with the saved state) is needed.
3. Pass counts vary by seed: row 21 passed in M281 and M282 and failed here; row 17 passed in M281 and M282 and failed here. A stance near the pass limit can pass on one seed and fail on another. The 51-stance results are no longer reproducible as single numbers; they vary from run to run.
4. Not rerun: the 51 stances (as asked).
