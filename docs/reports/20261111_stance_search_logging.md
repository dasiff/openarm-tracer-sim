# Stance Search Logging Implementation Report

**Date:** 2026-11-11  
**Scope:** Logging-only instrumentation of stance selection pipeline to enable arm pose comparison

## Overview

Integrated three-piece logging system into `src/stance_select.py` to capture:
1. **candidates_list.json** — all candidates attempted with check results and timings
2. **full_check_solutions.json** — arm joint solutions (q_left, q_right) per candidate
3. **dryrun_trajectories.json** — per-tick trajectory data from dry-run planner

No algorithm changes; logging only. All three JSON files saved to `data/demo_record/temp_stance_search/` per run.

---

## File Descriptions

### 1. candidates_list.json

**Path:** `data/demo_record/temp_stance_search/candidates_list.json`

**Purpose:** Track all candidates generated by edge sampler, their check results, and timings.

**Structure:**
```json
{
  "candidates": [
    {
      "number": 0,
      "base_x": 0.986,
      "base_y": 1.070,
      "heading_deg": -101.8,
      "pedestal_m": 0.1056,
      "wall_time_start_s": 0.12,
      "sim_time_start_s": 0.0,
      "checks": {
        "full_check": {
          "passed": true,
          "reason": "",
          "wall_time_end_s": 40.6
        },
        "dry_run": {
          "passed": true,
          "reason": "",
          "wall_time_end_s": 45.2
        }
      }
    }
  ],
  "accepted": 2
}
```

**Typical Size:**
- Small run (5 candidates): ~2 KB
- Medium run (25 candidates): ~8 KB
- Large run (50 candidates): ~15 KB

**Key Fields:**
- `number`: Candidate index (0-based)
- `base_x`, `base_y`: Stance position in meters
- `heading_deg`: Base heading in degrees
- `pedestal_m`: Arm pedestal height in meters
- `wall_time_start_s`: Wall clock time when candidate check began
- `sim_time_start_s`: Simulation time when candidate check began
- `checks`: Results of body_check (gate), full_check, and dry_run stages
- `accepted`: Index of the stance that was ultimately accepted

### 2. full_check_solutions.json

**Path:** `data/demo_record/temp_stance_search/full_check_solutions.json`

**Purpose:** Record the full check's arm joint solutions at each task point, showing what the checker "imagined" before execution.

**Structure:**
```json
{
  "0": {
    "left": {
      "point_0": {
        "q": [0.1, -1.2, 0.5, -0.8, 0.2, -0.1, 0.0],
        "point": "point_0",
        "angle": -101.8
      },
      "point_1": {
        "q": [0.2, -1.1, 0.6, -0.7, 0.3, 0.0, 0.1],
        "point": "point_1",
        "angle": -101.8
      }
    },
    "right": {
      "point_0": {...},
      "point_1": {...}
    }
  },
  "1": {...}
}
```

**Typical Size:**
- Small run (5 candidates, 3 points each): ~20 KB
- Medium run (25 candidates): ~100 KB
- Large run (50 candidates): ~200 KB

**Key Fields:**
- Top-level keys are candidate indices (as strings)
- Each candidate has `left` and `right` arm entries
- Each arm has task point names mapping to solutions:
  - `q`: Joint angles (7-element array in radians)
  - `point`: Task point identifier
  - `angle`: Approach or place angle at that point

**Usage:** Compare these imagined solutions against:
- Real arm trajectory from episode logs (qpos, qvel over time)
- Dry-run planner solutions (from dryrun_trajectories.json)

### 3. dryrun_trajectories.json

**Path:** `data/demo_record/temp_stance_search/dryrun_trajectories.json`

**Purpose:** Record per-tick trajectory data from the dry-run planner, showing what the solver converged to at each time step.

**Structure:**
```json
{
  "0": {
    "pick_over": {
      "name": "pick_over",
      "ok": true,
      "ticks": [
        {
          "t": 0.0,
          "q_cmd": [0.1, -1.2, 0.5, -0.8, 0.2, -0.1, 0.0],
          "pad_m": [0.5, 0.3, 0.2],
          "error": 0.005
        },
        {
          "t": 0.02,
          "q_cmd": [0.11, -1.21, 0.51, -0.79, 0.21, -0.09, 0.01],
          "pad_m": [0.51, 0.31, 0.21],
          "error": 0.004
        }
      ],
      "error": 0.002
    },
    "place_over": {...}
  },
  "1": {...}
}
```

**Typical Size:**
- Small dry-run (pick only, 50 ticks): ~30 KB
- Medium run (pick+place, 100 ticks each): ~80 KB
- Large run (pick+place+retreat, 150 ticks total): ~150 KB

**Key Fields:**
- Top-level keys are candidate indices (as strings)
- Each candidate has subtask entries (e.g., "pick_over", "place_over")
- Each subtask contains:
  - `name`: Subtask identifier
  - `ok`: Whether subtask succeeded
  - `ticks`: Array of per-tick snapshots:
    - `t`: Time within subtask (seconds)
    - `q_cmd`: Commanded joint angles (7-element array)
    - `pad_m`: Hand TCP position in meters [x, y, z]
    - `error`: Convergence error at this tick (meters)
  - `error`: Final error for this subtask

**Usage:** Analyze solver convergence over time, identify where planner gets stuck or diverges from full check solution.

## Naming Pattern

All files saved to run-specific directory:
```
data/demo_record/temp_stance_search/
├── candidates_list.json
├── full_check_solutions.json
└── dryrun_trajectories.json
```

Each run overwrites the previous temp files. For permanent storage, copy these files to run-specific directories or archive them.

## Limitations & Future Work

**Current Limitations:**
- Logging only; no visualization or comparison tools yet
- Arm solution format assumes fixed structure (may need refinement once actual check results are examined)
- Only captures candidates that pass full check or dry-run (filtered logging)

**Future:** 
- Build visualization to overlay all three arm poses (full check, dry-run, real) at same task point
- Compare end-effector error between imagined vs. real over time
- Identify systematic biases or solver convergence issues
