# Look-ups for David's open questions (2026-11-03)

Written for: David. Read-only. No simulation was run, no script that starts one was run, and no file in the repo was edited, staged or committed except this report (which is left untracked). No design, setting or fix is proposed; the candidates below are listed with the test that would separate them, and David decides.

Labels, kept apart throughout:
- **shown by the data/code**: read straight from a saved file or from a line of code (file and line given).
- **calculated from the data**: a formula applied to saved values (the formula is stated).
- **guess**: a possibility the data do not settle.
- **unknown**: not determined by what I could read.

Terms, plain: a **config** is the settings file (`src/task_config.py`); a **scene** is a MuJoCo model file (XML) that defines the bench, hotplate and beaker; **world model** is the knowledge base (`src/world_model.py`) that the scripted skills read object positions from; a **skill** is a scripted step (pick, place, and their phases OVER, DOWN, UP and so on); the **trim** is the sag correction, an integrator (a running sum of the hand's pose error, multiplied by a gain of 3.0 per second, `src/task_config.py` line 436) that nudges the path to cancel droop; **feedforward** is a torque added in advance to hold gravity; the **solver** is the inverse-kinematics (IK) solver that turns a hand target into joint targets; a **posture** term pulls the arm toward a standing pose (here the home pose); a **servo** is the motor controller at each joint; **openpi** is the policy framework the VLA would run; **tick** is one control step (150 per second).

## Summary in plain words

**(1) Which positions come from where, and which disagree.**
- The pipeline's *demo run* takes the hotplate and beaker positions at run time from the simulated scene, through the world model (`src/mpvi_modules.py` line 95; `src/world_model.py` lines 316–325). The *configured* numbers are written into the scene when the task loads (`src/task_beaker_hotplate.py` line 85).
- **The 0.80 and 0.65 mismatch is not a file disagreement.** The scene file `models/objects/hotplate.xml` line 13 says x = 0.80, and the config `src/task_config.py` line 51 says 0.80. The 0.65 comes from the **moved layout** that the demo applies at run time: `experiments/demo_video.py` line 43 (`SHIFT_X = -0.15`) and line 44 (`MOVED` dictionary). So the scene that a moved run builds has the hotplate at 0.65.
- **One real inconsistency**: `src/task_points.py` line 47 reads the *unshifted* config value (0.80) for the hotplate in every run, including the moved run. That function is used by the full check and by experiments, not by the demo pipeline (no call in the pipeline files, see look-up 1b).
- Every other pair I could compare agrees (look-up 1d): beaker position, hotplate position, bench top height, beaker height and diameter, beaker settle height, pedestal range, and site names. Five pairs could not be compared from files (robot base, second beaker, grasp and home joint poses, the hotplate's size, and the staging stance).

**(2) When and why the x trim winds up.**
- **Shown by the data:** the x part of the trim starts to move 22 ticks into the pick's OVER step (tick 9709, step start 9687), before any beaker is held (the held-mass ramp starts at tick 11181, `docs/reports/20261103_1640_bounce_check.md`). It reaches its largest value in place OVER: −15.09, −15.13 and −15.21 mm for 150, 200 and 250 g. So mass does not set its size. It then falls back to −5.5 mm at the start of DOWN and to −1.0 mm (200 g) at the end of DOWN.
- **Calculated from the data:** the trim's integrator law (it changes at 3.0 × the x error per second) gives an implied hand error of about **−0.6 mm** during pick OVER, **−5.5 mm** during place OVER, and **+0.7 mm** during DOWN (sign: negative means the hand is ahead of plan in +x). The hand's own x error against plan is **not logged** (the per-tick file has the reference height, not the reference x), so the direct x error is **unknown**.
- **Shown by the data:** the order of changes at each step start (200 g, same method as the lift analysis): the trim's x moves first (+22 ticks in pick OVER, +18 in place OVER), then the servo force (+30 and +31 ticks), then the hand (+35 and +35 ticks). Commanded joint targets change at about 0.19–0.22 s (the episode log is sampled at 10 Hz, so this is coarse).
- **Guess:** the solver's pull toward the home pose (a posture term, see look-up 2d) opens an x error during each OVER move, and the trim integrates it. The data do not separate the posture term from the servo's steady error or the arm's own weight. Candidates and the tests that would separate them are in look-up 2d.

**(3) Which pieces would and would not run under the policy.**
- **Would run under a bare policy (shown by the code):** the gravity feedforward for the arm's own bodies (`src/gravity_ff.py` lines 107–117, applied every tick at `src/control_loop.py` lines 925–930); the command bridge, which is on by default (`src/control_loop.py` lines 605–660; decision M241), and the routing and command writing that every source uses.
- **Would not run (shown by the code):** the sag trim and its freezes (`src/mpvi_modules.py` lines 71–80 and 376), the held-mass ramp (`src/held_mass_ramp.py`, with callers only in the scripted module), the lift-off detection and estimate (`src/mpvi_modules.py` lines 443–470), the gripper-open wait (lines 411–416), the holding checks at CLOSE (lines 425–433), and the skill-start reset (lines 265–268). All of these are triggered by scripted skill phases.
- **Partly:** the held part of the feedforward (`src/gravity_ff.py` lines 118–124) runs every tick, but its mass is zero unless a scripted weighing sets it, so under a bare policy it would be zero.
- **Dead in the live plans:** the handoff weight reading (`src/mpvi_modules.py` lines 471–488; no plan creates a "held" step), and the one-number and three-number weight fits when used only there.
- **Holding detection** is position-based in the scripted code (finger travel within a range, `src/mpvi_modules.py` lines 427–433 and 576–586) and contact-based in the simulator (`src/world_model.py` lines 286–304). No holding decision uses finger force. A gripper partly closed with no force counts as holding if its travel is in the range 3 to 40 mm (`src/task_config.py` line 446).

### 2c. Does the windup scale with mass, and is it present before the beaker is held?

- **Same at all three masses (shown by the data):** the largest x trim is −15.09, −15.13 and −15.21 mm (a spread of 0.12 mm over 150 to 250 g). Mass does not set its size.
- **Present before the beaker is held (shown by the data):** the trim is already −2.97 mm at the end of the pick's OVER step (tick 9915), before the grasp (CLOSE, tick 10999 to 11149), and before the held-mass ramp starts (tick 11181, `docs/reports/20261103_1640_bounce_check.md`). So the early windup is not caused by the held mass. The place OVER windup happens while the beaker is held, so the data here cannot say whether the held mass adds to it (it is the same at all masses, so the mass is not the driver).
- **Pick time against place time:** pick OVER ends at −2.97 mm; the place OVER peak is −15.1 mm. Both are with the same solver and servos, so the difference between them is not explained by the hold.

## Look-up 3: what sits below the policy

### 3a. How a policy action reaches the servos today

**The chain, in plain words (shown by the code):**
1. **Policy**: a function `policy(obs, t)` returns an array of actuator targets, one per actuator id (`src/policy_source.py` lines 1–8 and 23–36). For the arms this is 7 joint angles (radians) per side; for the gripper, a finger travel (metres); for the pedestal, a height (metres).
2. **Policy source** (`src/policy_source.py` lines 77–116, `step`): runs the policy once per tick, reads the arm joints from the applied targets, writes the policy's joint values into them (lines 96–103), and returns `{"mode": "arms", "arm_targets": …, "gripper": …}` and, if owned, `{"mode": "pedestal", …}`.
3. **Router** (`src/control_loop.py`, `_filter_by_route` at line 204, and the `routes` set by `make_policy_source`): gives each command field to the source that owns it.
4. **Command bridge** (`src/control_loop.py` lines 582–660): keeps the latest arm target per arm (`bridge_take`, line 623, for any arms command), checks it against the joint limits (`bridge_precheck`, line 605), and at 50 Hz (every 3rd tick, line 585 and the comment at line 36) moves the command toward the target by at most the joint speed limit (`bridge_update`, line 632).
5. **Writing the targets** (`src/control_loop.py` lines 441–453 `ctrl_block`, 554 `apply_cmd`): the accepted targets become the position targets for the servos, ramped over the tick.
6. **Gravity feedforward** (`src/control_loop.py` lines 925–930): once per tick it computes the arm's own gravity torque divided by the servo gain (`gff.torques(data) / gff.kp`) and adds it to the targets (`gff.apply_offsets`).
7. **Servo**: the MuJoCo position actuator at each joint, which pulls the joint toward its target with the gain kp (from the model).

**What the VLA outputs:** an array indexed by actuator id: seven joint targets per arm, a finger travel per gripper, and a pedestal height (`src/policy_source.py` lines 3–8). The openpi adapter is **not in `src/`**: `src/task_config.py` line 13 and line 139, and `src/sequential_policy.py` line 5, mention it as a future piece. So the exact openpi interface is **unknown** from this repo.

**Between the policy and the servos** (in order): the policy source, the router, the command bridge, the target writer, and the feedforward. The scripted skills (`src/mpvi_modules.py`, `src/orchestrator.py`) are not in this chain; they run as a separate command source (shown by `src/orchestrator.py` lines 34–35, "a command source of src/control_loop.py").
